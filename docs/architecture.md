# Architecture & Design

How HospitalShield AI is built, why it is built this way, and how the pieces behave under load and failure.

## 1. Design goals (in priority order)

1. **Correctness you can audit.** A hospital planner will defend decisions with these numbers. Every
   equation in `docs/equations.md` maps to a named function; conservation laws are enforced as runtime
   invariants, hour by hour.
2. **Reproducibility.** Identical input + seed + model version produces byte-identical output. The engine is
   a pure function; `run_id` fingerprints every response.
3. **Honesty.** Data provenance labels everywhere; limitations stated on every page; infeasible requests
   rejected with reasons rather than silently clamped; "optimal" plans labelled "best found within budget".
4. **Offline-first.** No cloud dependency for the core loop. Weather and LLM features are optional and
   degrade to labelled fallbacks.
5. **Small surface.** One process per tier, no message queues, no microservices, no authentication layer —
   the failure modes we don't have are the ones we can't debug at 2 a.m. before a demo.

## 3. Engine design

### 3.1 Purity boundary

`backend/app/simulation/` imports only `math`, `dataclasses`, `numpy` (for seeded sampling) and its own
modules. No `open()`, no `datetime.now()`, no module-level mutable state. All configuration enters through
validated frozen dataclasses; all timing is the integer hour index. This is what allows:

- byte-identical reproducibility (tested),
- golden snapshots as regression nets,
- property tests running thousands of scenarios per second (a 72 h run ≈ 9 ms).

### 3.2 The hourly loop (B3 order — implemented in `engine.py::_step`)

```
for hour h in 0..T-1:
  1 weather:      temperature_c[h], staff_access(h), delivery_fraction(h), arrival_mult(h)
  2 cooling:      cooling_kw = base + slope × max(0, temp − threshold); split critical/comfort
  3 interventions: surge (after delay) · staff moves · recalls (after lead, access-scaled)
                   shed request · resupply arrivals (after lead, delivery-scaled)
  4 power:        demand, grid supply, generator (fuel-limited), deficit XOR reserve,
                  critical_at_risk (never reduced), fuel burn
  5 staffing:     available = floor(roster × availability × access) + moves + recalls
                  staffed_capacity = floor(available × ratio); required = ceil(occ_prev / ratio)
  6 supplies:     consumption = weighted_occupancy × rate; deliveries; stock (never < 0); cover
  7 usable beds:  min(open, staffed) → derates if critical at risk / stockout → never eject
  8 patient flow: arrivals → waiting → ED cohorts (service, split) → boarding → admissions
                  (only into real capacity) → discharges (1/ALOS)
  9 record:       full row + per-unit status + margins + binding_constraint
```

After the loop: `alerts.py` (R01–R11 episodes) → `metrics.py` (B7 + Resilience Index) →
`failure_points.py` (margins, ranked failures, cascades) → `invariants.py` raises on any violation.

### 3.3 Deterministic vs stochastic flows

Fractional patient flows (e.g. 5.6 arrivals/hour, 25% hourly ED completion) must produce integers.
Deterministic mode uses **carry-forward accumulators**: residue carries to the next hour, so integer totals
match fractional expectations over the horizon without drift. Stochastic mode samples Poisson/Binomial/
multinomial from a local `Generator(PCG64(seed))` — never a global RNG. Both modes preserve conservation
exactly; ensembles vary only through the stochastic path.

### 3.4 Why integers everywhere for patients

Half a patient is a modelling lie that compounds. Integer flows make conservation checks exact (==, not
≈), keep the audit trivial, and cost nothing at this scale.

## 4. API design

- **Strict schemas** (`extra="forbid"`, explicit bounds, cross-field validators). Named presets are merged
  server-side *before* validation so a bare `{"scenario": "heatwave_power_outage"}` behaves identically to
  the UI preset, while explicit fields still override.
- **One error envelope** for every 4xx: `{error: {code, message, details[{field, reason, rule}]}}`. The
  engine's validation and feasibility errors map onto it (422 `VALIDATION_ERROR` /
  `INFEASIBLE_INTERVENTION`); the catch-all 500 returns a generic body with a request id and no trace.
- **Envelope metadata on every response**: model_version, input_hash, seed, assumptions, provenance,
  limitations. Clients can never mistake synthetic for real or precomputed for live.
- **Typed contract**: `frontend/openapi.json` → `frontend/src/types/api.ts` via openapi-typescript. No
  hand-written API types anywhere.
- **Hospital profiles**: uploads are validated by the same strict parser, stored under `data/hospitals/`,
  selected per request via `hospital_profile`. A 24 h sanity run after upload warns (not blocks) when a
  site's normal-operations profile already trips alerts.

## 5. Frontend design

- **One source of truth**: `RunContext` holds the latest result/comparison/plan and UI selections. Components
  render; they never recompute, re-threshold or hard-code. If the backend says occupancy is null (usable
  beds = 0), the UI shows "unavailable", not a guess.
- **Resilience**: skeletons while loading, empty states, an error boundary, cancelled requests, and the
  PRECOMPUTED offline fallback with editing disabled.
- **Accessibility**: status = colour + icon + text (never colour alone), keyboard-operable controls, aria
  labels on the SVG map and charts, reduced-motion respected, responsive to 360 px.
- **Every chart has a table alternative** (`ChartFrame`) — planners export, judges cross-check.

## 6. Failure modes and behaviour

| Failure | Behaviour |
|---|---|
| Backend down | UI loads precomputed snapshot, banners PRECOMPUTED, disables editing |
| Weather API down/timeout | Adapter retries once, falls back to labelled CSV, records a warning |
| SQLite unavailable | History/cache calls log a warning; simulations unaffected |
| Infeasible intervention | 422 with per-rule reasons; planner filters it and continues |
| Invariant violation | Engine raises `InvariantViolationError` — treated as a bug, fails loudly |
| Oversized/malformed request | 413/422 with the documented envelope |

## 7. Testing strategy

| Layer | Tool | What it proves |
|---|---|---|
| Units | pytest | Boundary arithmetic (occupancy clamps, deficit/reserve XOR, shed caps, staffing floors) |
| Properties | hypothesis (~660 examples) | Conservation laws, monotonicity, bounds, determinism — across random valid scenarios |
| Matrix | pytest parameters (1,008 cells) | No cell in the scenario×stress×intervention×stochastic×duration grid violates invariants or hides a clamp |
| Calibration | pytest | The four acceptance targets hold for the committed config |
| Golden | pytest + JSON snapshots | Output drift of every preset is caught |
| Contract | pytest + TestClient | Every endpoint, every error shape, byte-identical repeats, CORS |
| Components | Vitest + Testing Library | Units/deltas render, alerts highlight hour ranges, map follows backend status, backend errors show inline |

Coverage on the engine package: 92% (see `docs/test-report.md` for executed numbers).

## 8. Performance

One 72-hour run ≈ 9 ms (median), a full comparison ≈ 45 ms, 200-run ensemble ≈ 2.2 s, memory flat across
hundreds of runs. The planner respects both a simulation budget (≤ 600 runs) and a wall-clock budget (5 s),
reporting which one stopped the search. Numbers: `docs/test-report.md`.

## 9. Security & privacy posture

No PHI anywhere; uploads are facility-level operational parameters only. Exact-origin CORS with a production
guard against wildcards; request-size cap; generic 500s with request ids; no secrets in the frontend bundle;
no authentication by design (planning prototype) — any real deployment must put it behind the hospital's
identity layer.
